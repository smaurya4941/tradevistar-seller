# Backend gaps

The hand-off list for the backend team. The seller app is built against the API exactly as it is
today (no backend edits), so each item below is something the app works around. The list grows
with every phase: add a row when the app has to compensate for the API, and strike it through when
the backend closes it.

| # | Gap | What the app does today | What the backend could do | Found |
|---|-----|-------------------------|----------------------------|-------|
| 1 | **No mobile refresh token in the response body.** `POST /auth/login`, `/auth/login/otp`, `/auth/login/two-factor` and `/auth/refresh` return `{ accessToken, activeRole, user }` only; the refresh token travels solely as the `tv_refresh_seller` httpOnly `Set-Cookie`. The `x-tv-client: mobile` header is sent but the server does not act on it. | Reads the token from `Set-Cookie` in JavaScript, stores it in the Android Keystore (Keychain), and presents it as `Cookie: tv_refresh_seller=...` with `credentials: "omit"` on refresh. Needs `Set-Cookie` to be visible to JS on the device; if a device or OS version hides it, sign-in cannot persist (see Phase 0 test protocol). | Return `refreshToken` and `refreshExpiresAt` in the body when `x-tv-client: mobile` is set. The client already prefers the body over the cookie. | Phase 0 |
| 2 | **No `GET /app/config`.** The endpoint is not served (404). | Falls back to `MIN_SUPPORTED_VERSION`, `LATEST_VERSION` and `PLAY_STORE_URL` from the flavor env file; the call is isolated in `core/appConfig/appConfigService.ts` and switches to the server answer with no app change once it exists. | Serve `{ minSupportedVersion, latestVersion, updateUrl, maintenance, features, forceUpdate }` per platform and version. | Phase 0 |
| 3 | **No push device registration or sender.** There is no endpoint to register an FCM token and nothing sends push notifications. | None yet; push is Phase 2. | Add device registration (token, platform, app version) and a sender for the notification types the web already creates. | Phase 0 |
| 4 | **Account deletion is requested but never executed.** The request is recorded but no job deletes the account. | Not offered in the app until it is real. | Execute the deletion job, or expose its status. | Phase 0 |
| 5 | **Maintenance has no read endpoint the app can ask.** `MAINTENANCE_MODE` (503) pauses writes only; reads always pass. `GET /platform/notices?audience=seller` lists live and upcoming windows, but a refused write is still the only proof that a given action is paused. | Phase 1: a refused write shows an inline "Paused for maintenance" sheet with "Available again at ..." from `details.endsAt`, and re-reads the notices so the banner is current. Nobody is signed out and reads keep working (this corrects Phase 0, which sent the whole app to a maintenance screen). The full-screen block remains only for a future `/app/config` maintenance flag (gap 2). | Add `maintenance` to `/app/config` (gap 2) if a hard stop is ever wanted. | Phase 0 |
| 6 | **Role-mismatch errors have no stable code.** A buyer-only account on the seller portal gets 403 "This account has no seller access - register as a seller first"; an OTP login for an unknown identifier gets 401 "No seller account with this identifier". | The app shows the server message as sent, and offers "Create a seller account" when the text says to register as a seller. The match is on the wording, so a reworded message loses only the shortcut, not the error. | Return codes such as `NO_SELLER_ACCESS` and `UNKNOWN_ACCOUNT`. | Phase 1 |
| 7 | **Reset password checks the code only at the final submit.** `POST /auth/forgot-password` sends a code, but nothing verifies it until `POST /auth/reset-password` receives the new password. | The code step only checks the format. A rejected code at the last step sends the seller back to the code step with the reason, keeps the typed password, and allows resend. | A verify-only endpoint for reset codes, as there is for registration. | Phase 1 |
| 8 | **Registration category is free text on the web but a code in the invitation prefill.** The backend stores `categoryCode` as an unvalidated string (max 100); the web register form sends whatever was typed ("Textiles") while `GET /onboarding/invitations/prefill` returns a category code. | The app offers a picker over the top level of `GET /categories` and sends the chosen category `code`, so values match the prefill. An invitation code that is not in the list is still sent as it came. | Validate `categoryCode` against `categories.code`, and make the web form a picker. | Phase 1 |
| 9 | **The web register page links Terms and Privacy to `#`.** | The app opens `TERMS_URL` / `PRIVACY_URL` from the flavor env, which default to the web info pages (`/info/terms-of-use`, `/info/privacy-policy`). | Point the web links at the same pages. | Phase 1 |
| 10 | **App Links need `/.well-known/assetlinks.json` on the web host.** The manifest declares the https `autoVerify` filter for `/seller`, but Android only opens links in the app once the host serves the file with the Play App Signing certificate SHA-256. | Until then Android shows a chooser, and the custom scheme `tradevistarseller://invitations/accept?token=...` always works. | Serve `assetlinks.json` for `com.tradevistar.seller`, `.staging` and `.dev` from the web host. This is a deployment item on the web side. | Phase 1 |
| 11 | **FULL maintenance and sign-in/registration.** From `siteNoticeRules` (read, not run): a FULL lock exempts `/auth/*` except `/auth/register`, so sign-in, OTP and password reset keep working during a full window while seller registration is paused. | Registration shows the server 503 message through the paused-for-maintenance sheet. Not exercised against a running backend. | Confirm on staging with a FULL notice. | Phase 1 |
| 12 | **Reset password revokes every session.** `resetPassword` calls `revokeAllForUser` (read in `authService.ts`), so a reset signs the seller out everywhere, including a phone that was signed in. | A signed-in phone is signed out at its next refresh and lands on sign-in with the "Please sign in again" message. Not exercised against a running backend. | None needed; noted so support can explain it. | Phase 1 |
| 13 | **No stable error code for a refused registration ticket.** Registration answers 401 "Verification ticket was already used" without saying whether the mobile or the email proof was refused. | The app clears both tickets and returns to the mobile step with the typed details kept; a 409 naming the email or mobile returns to the step it names. | Return which proof failed, or a code per case. | Phase 1 |
| 14 | **`GET /me/access` carries no organization context.** Accepting a team invitation changes the seller workspace, but nothing in the response says which organization is active. | After accepting, the app refreshes the session (`/auth/refresh`) so the new token can carry the organization, then drops every cached query. The refresh is harmless if it fails. Whether org-scoped calls need it is unconfirmed. | Document how the active organization reaches the token. | Phase 1 |
| 15 | **SMS autofill needs Google Play services.** The native SMS User Consent module (`TVSmsConsent`) is ported from the buyer app and compiled into the Android build, but it was not exercised on a device. | Where Play services are missing the module reports unavailable and the seller types or pastes the code; Google Keyboard code suggestions still work through `autoComplete=sms-otp`. | None. | Phase 1 |
| 16 | **No push sender or device registration (restates gap 3 with the Phase 2 behaviour).** `POST /me/devices` does not exist and nothing sends a push, so a closed or killed app is never alerted. | While the app process is alive: a banner and the platform sound in the foreground, a Notifee system notification in the background for rows flagged `metadata._push`. A cold start never alerts for old rows (the seen list is kept in MMKV, capped at 2,000 ids, cleared on sign-out). Device registration is wired but dormant: a 404 is remembered for a day, so no launch calls the missing route, and it starts working with no app change once the route ships. | Add device registration and a sender for the notification types the web already creates. | Phase 2 |
| 17 | **Support ticket creation and replies have no idempotency.** `POST /support/tickets` and `POST /support/tickets/:id/messages` take no idempotency key, so a retry after a timeout can post twice. | Before sending the same ticket or reply again after an ambiguous failure (no connection, timeout, 429, 5xx) the app re-reads the ticket list or the thread and treats a match created since the first attempt as success. Only then does it resend. | Accept an `Idempotency-Key` on both routes. | Phase 2 |
| 18 | **`GET /seller/dashboard` returns the revenue and order series even when insights are locked.** Only `topProducts` and `aiInsights` are withheld; the web hides the rest in its UI. | The gate is a UI rule: Analytics asks `GET /seller/subscription/usage` for an `INSIGHTS_ANALYTICS` entry with `included`, and Home hides its chart section (showing a small "Unlock analytics" card) when `insightsLocked` is true. | Withhold the series server-side for plans without the feature. | Phase 2 |
| 19 | **The web analytics page computes catalog mix and quote conversion from the first 100 products and quotes only.** | The app reads the same first 100 (`GET /seller/products` and `/seller/quotes`, page 1, limit 100) so both products agree, says so under both figures, and keeps the model behind `listCatalogProducts` / `listQuoteRecords` so Phase 5 can switch lists. | Offer aggregate endpoints (counts by category, quotes by status and month). | Phase 2 |
| 20 | **"vs previous period" is a split of the selected window, not the true previous period.** The web compares the first and second half of the 3, 6 or 12 months shown. | The same arithmetic, labelled honestly: "vs earlier half of period". | Return the true previous window from the dashboard. | Phase 2 |
| 21 | **"Share Storefront" copies the seller portal's own address.** No public storefront URL is exposed to the seller side. | The action is left out of Quick actions. Export Catalog is also left out until the Phase 5 product list exists. | Expose the seller's public store URL on the profile or dashboard. | Phase 2 |
| 22 | **Search results and notifications carry web paths.** `GET /seller/search` returns `href` such as `/seller/dashboard/orders?order=<id>`, and notifications carry web paths in `metadata.actionUrl`. | `searchRoute`, `notificationRoute` and `routeForHref` read only `/seller/` paths (no scheme, no `//`, no `..`) and map them to screens, keeping the query for the target phase (orders `order`/`buyer`/`status`, products `q`, inquiries `rfq`, wallet `txn`). A link with no app screen offers "Open on web". Phases 5-8 must read these parameters in their screens. | Return typed targets (type and id) beside the path. | Phase 2 |
| 23 | **`metadata._push` is set by the server but its rule is unconfirmed.** The app treats `_push: true` as "the seller's Push preference for this category is on". | Background alerts are raised only for rows with `_push === true`. | Confirm (and document) that `_push` is set only when the Push channel is on for that category. | Phase 2 |
| 24 | **SMS notification preferences are stored but not delivered.** The SMS gateway carries sign-in codes only. | The preference screen says so, and the switch still saves. | Deliver SMS alerts, or hide the channel. | Phase 2 |
| 25 | **There is no unread marker on support tickets.** A reply from support is not flagged on the ticket row. | The list shows the ticket's last activity; a `support.*` notification and its badge are the hint, and the thread refreshes on the socket event and every 30 seconds. | Add `unreadByUser` or a last-read time to tickets. | Phase 2 |
| 26 | **An admin-uploaded notification sound cannot change the Android system notification sound.** Android takes a notification's sound from its channel, which an app cannot change remotely. | The uploaded sound (`GET /notifications/sound`, versioned) plays for arrivals while the app is open and honours the phone's silent mode (a small native module reads the ringer mode). Settings says that phone alerts use the channel's own sound. | None; documented so support can explain it. | Phase 2 |
| 27 | **The seller footer's Terms page is `terms-of-use`, not `terms-of-service`.** The Phase 1 defaults assumed the buyer slug. | `TERMS_URL` and `HELP_URL` now default to `/info/terms-of-use` and `/info/help-support`. | 28 | **The seller web footer enquiry needs the audience.** `POST /footer/enquiries` takes `audience`; without it the page is looked up in the buyer footer, so a seller-only page slug is refused. | The app sends `audience: "SELLER"` with every enquiry. | Default the audience from the page slug. | Phase 2 |
| 29 | **Appearance (light, dark, system) is not offered in Settings.** The design tokens include a dark palette, but the Phase 0 and 1 screens read the static light colours. | Left out so the app never shows a half-dark screen; new charts already follow the theme. | Not a backend item: move the older screens to `useThemeColors()` first. | Phase 2 |
| 30 | **Non-PDF files are accepted for seller documents.** Only the KYC-evidence upload route (`/media/kyc/:type`) enforces PDF; `/media/seller-documents/:type` accepts images and DWG. | 31 | **The password rule differs between screens.** Change password requires 8-128 characters with a lowercase letter, an uppercase letter and a digit (`changePasswordDto`); sign-up and reset only check `MinLength(8)` (`registerSellerDto`, `passwordDto`). | The change-password screen enforces the stricter rule and explains it in the hint; sign-up and reset keep the length-only check so the app never refuses what the server accepts. | Use one rule for register, reset and change. | Phase 3 |
| 32 | **Account and Business share one profile version and overlap in fields.** Both edit display name, description, business email, phone and website. | Each save refetches both screens, and a stale answer keeps the seller's edits on top of the new server copy. | Give each screen its own version, or merge the two resources. | Phase 3 |
| 33 | **The primary category is an unvalidated string.** `primaryCategoryCode` is not checked against the category tree, on the web it is a free-text box. | The app offers a picker over the top-level categories and stores the chosen code. | Validate the code against `GET /categories`. | Phase 3 |
| 34 | **Account closure is request-only.** The preflight reports blockers and a grace period, but no job executes the closure and the web button is disabled. | The app does not show a button that does nothing: with no blockers it opens a pre-filled support ticket, which is also the in-app deletion request Google Play expects. | Execute closures, or expose their state. | Phase 3 |
| 35 | **Compliance asks for more documents, but the web seller portal never shows them.** `GET /me/kyc` returns `documentRequests` (document types and notes, status OPEN), which only the buyer app displayed. | The Documents screen shows a "Compliance asked for: ..." banner from the open requests. | Show the same banner on the web. | Phase 3 |
| 36 | **A password change and a login contact change invalidate the current access token.** Both bump the account version on the server. | `SessionEngine.renewSession()` refreshes straight away after either change, so the first request does not fail once and rely on the retry. | Return a fresh token in the response of these two calls. | Phase 3 |
